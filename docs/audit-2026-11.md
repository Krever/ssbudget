# Project audit, November 2026

Made on 2026-11-19 by five read-only review passes (backend, frontend, tests and delivery, security and operations, product), then
checked by hand where marked. This file is the list of all findings, so that none is lost. Change the status of an item when you
work on it; add the commit.

Status: `[ ]` open, `[x]` done, `[-]` decided against. Effort: S (hours), M (a day or two), L (more).
"Checked" means that the claim was confirmed in the code or in the deployment by a second look, not only by the review pass.

Paths: `B/` = `backend/src/main/scala/ssbudget/backend/`, `F/` = `frontend/src/main/scala/ssbudget/frontend/`,

## Batch 1: small fixes (done, commit c80384d)

- [x] **Session cookie not `Secure` in production, no `SameSite`, no HSTS.** The flag came from `SSBUDGET_COOKIE_SECURE`, which
  was set nowhere. Checked: not in `fly.toml`, not in the fly secrets. Now: `Secure` when all `SSBUDGET_RP_ORIGINS` are https,
  `SameSite=Lax`, and an HSTS header on https deployments. `B/AuthRoutes.scala`, `B/ServerBuilder.scala`.
- [x] **Password login had no attempt limit, and each attempt takes 64 MB.** Now: at most two Argon2 runs at a time, and a lock
  that doubles after 5 failures in a row (`B/auth/LoginThrottle.scala`, `B/auth/PasswordService.scala`).
- [x] **Dashboard "Edit Balances" lost a cent** (`(d * 100).toLong`: 19.99 became 19.98; checked) and wrote every manual account
  on each save. Now: the one parsing rule (`InlineEdit.parseCentsOpt`), and only changed balances are written.
  `F/pages/DashboardPage.scala`.
- [x] **Deletes ran on one click.** Category, account, rule, bank connection, card group, currency. Now a two-click button
  (`Loading.confirmActionButton`: the first click arms it for 4 seconds), passkey delete included.
- [x] **Test mode turned on when the variable only existed**, also with the value `false`, and with no warning. Now: only `1` or
  `true`; a warning at start; the app refuses to start in test mode when `SSBUDGET_RP_ID` is not `localhost`. `B/Main.scala`.
- [x] **Database import did not migrate and accepted any SQLite file.** Now: a file with no migration history is refused, a file

## Security and operations

- [x] **A session alone can export or replace the database and add or delete a passkey**, while an MCP token needs an identity
  proof. Session tokens are stored in plain text (`M/V2__auth_schema.sql`, `B/db/repository/SessionRepository.scala`), so a
  backup file holds working logins. Fix: store SHA-256 of the token (as `McpTokenService` does), leave `sessions` out of the
  export, ask for an `IdentityProof` on import, export, passkey register and passkey delete. M.
  Done: `sessions` holds the SHA-256 digest (V31 ends the old sessions: one new login per device); export, import, passkey add and
  delete need a recent proof on the session (`validateConfirmed`). `sessions` stays in the export: it holds digests only.
- [x] **No copy of the database before a migration.** Checked: fly.io keeps a daily volume snapshot for 5 days, so the data is
  not without backup; what is missing is a copy just before Flyway runs, and anything older than 5 days. Fix: in
  `docker/entrypoint.sh`, `sqlite3 .backup` to `/data/backups` before the app starts, keep the last N; think about an off-machine
  copy. S.
  Done: `docker/entrypoint.sh` copies the database to `/data/backups` before each start and keeps the newest 5. An off-machine copy is still open.
- [x] **No fly health check** (`fly.toml` has no `[[http_service.checks]]`; the Docker `HEALTHCHECK` is not read by fly). A deploy
  whose migration fails can look successful. Fix: a check on `/api/health` with a grace period for the JVM start. S.
  Done: a check on `/api/health` in `fly.toml`.
- [x] **`/api/auth/setup` is open when no password hash exists, also when passkeys exist**, and accepts an empty password
  (`B/AuthRoutes.scala`, `setupPassword`). Matters on a fresh or restored instance. Fix: a one-time setup secret from the
  environment or the boot log, refuse when a passkey exists, a minimum length. S.
  Done: setup is refused when a passkey exists, and a password has 8 characters or more (setup and change). Not done: a one-time
  setup secret.
- [x] **No CSRF or Origin check on cookie routes.** `SameSite=Lax` (batch 1) closes most of it. Still open: a middleware that
  refuses non-GET requests on `/api` and `/metabase` whose `Origin` is not an RP origin. S.
  Done: `Hardening` refuses a write whose `Origin` is not the host of the request or a configured origin, on the app's routes and on
  the analytics proxy. The dev and e2e proxies keep the Host header for this.
- [x] **No security headers** (CSP, `nosniff`, `frame-ancestors`, `Referrer-Policy`) on the app's own responses. S.
  Done: `Hardening.headers` (content policy, frame options, nosniff, referrer policy). Checked in a browser on the release build: no
  violation on the Dashboard, Periods, Transactions and Settings pages. Not checked: the Analytics page with Metabase.
- [x] **No request size limit outside `/mcp`.** Fix: `EntityLimiter` of about 1 MB on the auth routes, a larger explicit limit on
  the import route. S.
  Done: 2 MB for an ordinary request, 512 MB for the database import.
- [x] **One global pending WebAuthn challenge**, replaced by a public route (`B/auth/WebAuthnService.scala`). A stranger can make
  each passkey login fail. It is denial of service, not a bypass. Fix: key the pending challenges by a random id with an expiry. M.
  Done: `PendingChallenges` keeps each request under its own challenge, read from the answer of the device; 5 minutes, one use,
  at most 1000 kept. No change of the API.
- [x] **Expired sessions are never deleted** (`SessionService.cleanupExpiredSessions` has no caller), a password change keeps all
  sessions, and there is no "sign out everywhere". `last_used_at` is written on every request. S.
  Done: expired sessions go at each start and each login; a password change ends every other session; `last_used_at` is written one
  time in a minute at most. Not done: a "sign out everywhere" button.
- [x] **Failures of background work go to stdout only** (`B/service/BudgetSnapshotTrigger.scala`, `B/Routes.scala`
  `freeMoneyHistory`). If the daily snapshot starts to fail, nothing shows it. Fix: keep the last success or error and show it on
  the Dashboard; log at ERROR level. M.
  Done: `BackgroundHealth` logs the failure as an error and keeps it until the task succeeds; the notice strip shows it.
- [x] **Metabase proxy does not renew the service session after a 401** (`B/analytics/MetabaseClient.scala`). "Explore" can stop
  working until a restart. S.
  Done: the proxy drops the token on a 401 and sends a request with no body again (`AnalyticsProxySessionSpec`).
- [ ] **Container hardening.** The image runs as root; the Metabase jar is downloaded with no checksum; the local Enable Banking
  key and the backups in `~/Downloads` have mode 644. S.
  Part done: the two JVMs run as a service user (the container starts as root only to give the data volume to that user), and the
  build checks the SHA-256 of the Metabase jar. Tested in a local container on a volume that the old image had written as root.
  Open: the mode of the local Enable Banking key and of the backups in `~/Downloads`, which are on the machine of the user.

Checked and sound: every data route needs a session; session and MCP tokens are 256-bit random; MCP tokens are hashed and never
logged; the Metabase proxy checks the app session first and is bound to loopback; static files cannot leave their directory; SQL
is parameterised; no secret is in git or its history; no CORS is configured.

## Found after the audit

- [x] **A currency exchange inside Revolut counted as income and as spend.** Both entries ("Exchanged to PLN") have no counterparty, so
  they were not seen as a transfer between own accounts; each exchange added its amount to "In" and to "Out" of the period. Now such
  entries are internal (`internalRemittancePatterns`). Saved and market result did not change.
- [x] **"Still to save" did not agree with "Saved" on the same page.** The plan was counted down with the opposite of the `fromSavings`
  term, which sees only what left a spending account. Pay that stayed on a savings account (Revolut USD) was not counted: "Saved" was
  above the plan and "Still to save" was 1,010. Now both are one figure: the change of the savings balances plus what was moved into
  investments. The daily record reads the ledger in each pass while the open period has a plan.

## Facts to keep in mind

- The backend has no scheduler; the machine suspends, and snapshots run off page traffic. A function that must run with nobody in
  the app is not possible today.
- The single-connection SQLite pool serialises all work. That is correct for one household; a long transaction makes every other
  request wait.
